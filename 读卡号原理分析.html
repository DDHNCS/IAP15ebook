1 · 读卡号到底在做什么

“读卡号” = 主控通过 RC522 芯片向天线招呼 → 检测到卡 → 问它“你是谁” → 卡片把自己的 UID（4 字节序列号）+校验字节报回来 → 主控校验无误后打印。整个过程发生在一张没有电池的卡片和一块蓝色小 PCB之间，本质是 13.56 MHz 射频场里的能量与数据交换。

一次成功读卡号，在软件上只走两段命令 + 一次校验：

① 寻卡 REQA
主控问：场内有卡吗？
卡答 ATQA
回 2 字节类型；软件长度=0x10(16bit)
② 防冲突 0x93/0x20
问：报上你的 UID
卡回 UID+BCC
5 字节；长度=0x28(40bit)
先记一句核心：寻卡(REQA)用“7 位短帧”，防冲突/休眠用“完整 8 位字节”。本程序早期正是把这一者弄混，导致永远读不到卡号（见第 5 节详解）。

2 · 数据通路全景：主控 → 卡片

链路虽长，但从软件看就一句话：主控只通过 SPI 写 RC522 的寄存器。真正“发电”、调制 13.56 MHz、做 ISO14443 编解码、防冲突的，全是 RC522 芯片自己完成。主控甚至连 13.56 MHz 波形都不用产生。

图 2-1　主控只写寄存器；真正驱动磁场的链路是“①→⑤”。橙色为 13.56 MHz 射频双向媒介。

3 · 卡片为什么“不用电池”

能量从哪来（电磁感应取电）

天线持续辐射 13.56 MHz 交变磁场。卡片内线圈 LC 谐振到同频率，切割磁感线产生感应电压，经整流给卡内芯片供电。电压达约 2 V 芯片即“醒来”。所以卡片无需电池。

这也解释了两个现象：卡片必须靠近并平行于天线才供电给足（1~3 cm）；金属/大块地平面会吸收磁场从而读不到。

数据怎么回来（负载调制）

卡没有功率“主动广播”，它按数据瞬间改变自身线圈负载，反射回读卡器天线端的微弱幅度变化。RC522 前端灵敏地解调出这些变化并还原成数据。这就是无源卡通信的标准方式。

4 · 一次寻卡对话：ISO/IEC 14443A

卡片采用 ISO/IEC 14443 Type A（MIFARE）协议。主控要掌握的，只是“发命令→等应答→按长度判断收对没”的对话。

图 4-1　一次 UID 读取的完整对话。注意寻卡是一条“短帧”，防冲突是“整字节帧”——正是第 5 节的关键。

“自动寻卡模式”其实就是主循环里反复执行上面这段；执行得越快，卡的应答与“刷卡体验”越接近实时。真实程序还加了失败重试 3 次，以容忍射频抖动带来的零星失败。

5 · 核心命门：BitFramingReg 位长

这是本程序早期“能读到 Ver、却永远读不到卡号”的真正根因。BitFramingReg(地址 0x0D)的低 3 位 TxLastBits 决定“发射帧的最后一个字节真正包含几位”。

❌ 早期：公共收发函数里统一定成 7 位

// PcdComMF522() 对所有命令无条件执行
WriteRawRC(BitFramingReg, 0x07);

// 后果：
// REQA(7位短帧)   → 0x07 恰好正确 ✓
// 防冲突0x93 0x20 → 也被按7位截断 ✗

防冲突命令本该是2 个完整 8 位字节，却被当成 7 位短帧去编码。卡片收到畸形请求 → 不回 UID → PcdAnticoll 稳定返回错误。

✅ 修复：由各命令自行设置

// PcdRequest()   —— 寻卡，确需7位短帧
WriteRawRC(BitFramingReg, 0x07);

// PcdAnticoll() / PcdHalt() —— 完整字节
WriteRawRC(BitFramingReg, 0x00);

实测通过：ATQA=0400 → AColl=OK → UID=EA5DDD06（BCC 校验一致）。

要命的设计点：“一眼该怎么发”属于命令语义，必须由发命令的高层 API（PcdRequest / PcdAnticoll）设置；收发的公共函数只负责“搬运数据、等中断、读 FIFO”，它并不该去规定帧的位数。我早期把这个语义错误地下沉到了公共函数。

6 · SPI 读写一个寄存器

RC522 是 SPI 从机。主控先发一个地址字节，再跟 0~n 个数据字节即可完成读或写。

图 6-1　RC522 的 SPI 地址字节：读标志在 bit7(最高位)，不是 bit0。

初次移植时若把读标志错放成 |0x01（bit0），会让每次“读”都跑到错误寄存器，从而出现 Version=0x77 这类“读得到但值错”的怪象。对照 NXP 手册 Table 8 就能一步到位。

7 · UID 与 BCC 校验

防冲突后卡片返回 5 字节：前 4 字节是 UID，第 5 字节是 BCC。校验方法是让后 4 字节的校验值应当等于 BCC：

代码里的实现：边拷贝 4 字节边累计异或 check ^= buf[i]，最后与返回的第 5 字节比较。不等则丢弃重试，避免把“冲撞时的脏数据”当成卡号。

8 · 程序分层与主循环

整个工程按“自底向上”分成清晰的 4 层。越下层越贴近寄存器，越上层越贴近“能不能刷到卡”：

层级文件/职责读卡中扮演的角色
④ 应用层main.c 主循环 ReadCardUID()决定“无卡继续扫、有卡读 UID 并打印”，并做重试
③ 14443A APIrc522.c 下半PcdRequest(寻卡) / PcdAnticoll(防冲突) / PcdHalt(休眠)，各自设对 BitFramingReg
② 收发核心rc522.c 中PcdComMF522 搬 FIFO、等中断、收数据；CalulateCRC
① 寄存器访问rc522.c 上半 + rc522.h(引脚)WriteRawRC / ReadRawRC / SPI_Init 与 SPI1 引脚 sbit

主循环本质上是一台“状态机”：

void main(){
  SPI_Init(); RC522_Init(); // 开SPI → 复位+ISO14443配置+开天线
  Uart1_Init();                // 打开调试串口
  print("RC522 Ver=xx");      // 自检：0x91/0x92 表 SPI 通
  while(1){
     ReadCardUID();            // 寻卡→(可)防冲突→校验→打印UID
     DelayMs(150);             // 简单消抖，防“同卡反复刷”
  }
}

ReadCardUID 的微观流程

if( PcdRequest(REQALL, &type)==OK ){  // ① 找到一张卡
    DelayMs(10);
    for(retry=0; retry<3; retry++){    // ② 防冲突失败重试3次
        if( PcdAnticoll(uid)==OK ){  // ③ 拿到UID(已含BCC校验)
            LED ^= 1;  print("UID "); // ④ 翻转LED + 打印卡号
            for(i=0;i<4;i++) hex(uid[i]);
            PcdHalt();  return;       // ⑤ 让卡休眠，本轮结束
        }
        DelayMs(5);
    }
}

为什么用 REQALL(0x52) 而不是 REQIDL(0x26)：REQALL(WUPA) 能唤醒任意状态的卡(包括刚被 14443A 高层命令弄“睡/暂停”的卡)，防冲突偶发失败重试后仍能唤醒，读卡成功率高，也避免把卡“卡死”在奇怪状态。
